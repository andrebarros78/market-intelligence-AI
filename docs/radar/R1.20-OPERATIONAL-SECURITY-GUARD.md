# R1.20 — Guardião de Segurança Operacional Read-Only

## Objetivo

Implementar a seção 18 da especificação soberana do Radar como controles executáveis, e não apenas como convenções: durante o Módulo 01, o runtime deve permanecer somente leitura e qualquer acesso Mercado Livre deve falhar fechado quando método, host, caminho, query, headers ou transporte violarem a política operacional.

## Lacuna encontrada antes da implementação

O projeto já possuía boas proteções isoladas:

- `Settings.read_only=true` por padrão;
- `allow_marketplace_writes=false` por padrão;
- `MercadoLivreReadOnlyAdapter` usa GET;
- rede real bloqueada por padrão;
- redirects desabilitados;
- telemetria sanitizada;
- credenciais removidas do payload analítico.

Entretanto, esses controles ainda não formavam um invariante central verificável.

A inspeção identificou pontos concretos para endurecimento:

1. `create_app()` podia ser construído com `read_only=false` e `allow_marketplace_writes=true`, apesar de o Módulo 01 ser soberanamente read-only;
2. headers adicionais eram aplicados depois do `Authorization`, permitindo que um chamador interno sobrescrevesse o header de autenticação;
3. caminho, query e host não eram validados por uma única política antes do transporte;
4. qualquer `AsyncBaseTransport` fornecido era tratado como transporte sintético, embora um transporte customizado pudesse ter comportamento de rede próprio;
5. identificadores inseridos em paths não tinham um guardião específico de segmento.

Nenhuma exploração externa foi executada. A correção foi validada exclusivamente com transportes sintéticos e CI.

## Política central

Módulo:

`market_intelligence.core.security`

Versão:

`module01-security@1.0.0`

A política é fail-closed e produz códigos estáveis de violação.

### Runtime do Módulo 01

O processo recusa inicialização quando:

- `read_only=false`; ou
- `allow_marketplace_writes=true`.

Isso transforma a restrição read-only em invariante de runtime do Módulo 01.

### Request Mercado Livre

Antes de qualquer transporte, a política exige:

- método `GET`;
- HTTPS;
- host exato `api.mercadolibre.com`;
- porta padrão/443;
- nenhuma credencial embutida na URL;
- nenhum fragmento;
- resource path local iniciado por `/`;
- nenhum host absoluto ou scheme-relative;
- nenhuma travessia `.`/`..`, inclusive codificada repetidamente;
- nenhuma barra invertida ou caractere de controle.

### Identificadores

IDs usados como segmentos de path devem:

- ser strings não vazias;
- respeitar limite de tamanho;
- não conter `/`, `\\`, `?`, `#`, `%` ou controles;
- não ser `.` ou `..`;
- não conter whitespace periférico.

### Headers adicionais

O chamador só pode acrescentar:

- `accept`;
- `x-format-new`.

São bloqueados, entre outros:

- `authorization`;
- `proxy-authorization`;
- `cookie`;
- `host`;
- `x-forwarded-host`;
- headers arbitrários fora da allowlist.

O `Authorization: Bearer ...` é escrito pelo adaptador depois da validação e não pode ser sobrescrito pelo chamador.

### Query string

São bloqueados parâmetros com nomes sensíveis, sufixos `_token`/`_secret`, caracteres de controle e valores que ecoem o access token corrente.

### Credential echo

A segunda revisão, executada depois de um primeiro CI verde, encontrou uma lacuna adicional: um chamador poderia tentar colocar o access token dentro de um path estruturalmente válido ou dentro de um header permitido como `Accept`.

A correção adicionou `assert_no_credential_echo(...)` à política central. Antes da construção da request, path e valores de headers adicionais são examinados e qualquer eco do access token é recusado com `mercadolivre_credential_echo_blocked`.

O CI que havia passado antes dessa descoberta não foi aceito como gate final.

### Transporte

- sem transporte e sem `network_allowed=true`: rede bloqueada;
- `httpx.MockTransport` é reconhecido como transporte sintético de teste;
- transporte customizado arbitrário não ganha implicitamente permissão de rede;
- rede real continua não habilitada pela aplicação desta release.

## Observabilidade e verdade operacional

`/ready` expõe:

- `read_only=true`;
- `marketplace_writes=false`;
- versão da política de segurança.

`/v1/system/capabilities` expõe uma seção `operational_security` com os controles efetivamente presentes, incluindo método/host permitidos, bloqueio de override de Authorization, guardas de path/query, ausência de scraping fallback e rede real desabilitada no runtime atual.

## O que a R1.20 não faz

- não habilita OAuth real;
- não ativa rede real Mercado Livre;
- não executa scraping;
- não cria escrita no marketplace;
- não cria credencial;
- não faz deploy;
- não altera banco;
- não inventa integração de IA externa;
- não declara que dados podem ser enviados a IA externa sem futura camada de minimização específica.
